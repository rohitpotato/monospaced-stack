> **TL;DR:** I run coding agents in my homelab, and I treat every tool call they make as untrusted code. Each agent lives in a Kata Container (a microVM with its own kernel), I drive it from my phone over Claude Code's Remote Control with no inbound ports, and it holds only read-only cluster access and repo-scoped Git tokens. Isolation limits *where* damage can happen. Scoped credentials limit *how much*.

Coding agents don't just generate text. They run shell commands, edit files and make network calls. That's what makes them useful, and it's also the whole problem.

An agent reads whatever you point it at: a README, an issue comment, a log line, a web page. If any of that text contains instructions, the agent may follow them. One poisoned comment, and a tool call becomes a remote shell on your machine.

So I built my setup around one assumption: **every tool call is untrusted code.** Not "probably fine", not "it's my own repo". Untrusted, the same way I'd treat code from a stranger's pull request.

## Isolation: a kernel of its own

A normal container is a process with some namespaces and cgroups around it. It shares the host's kernel. That's fine for my own services, but for an agent running arbitrary commands it means one kernel exploit is a full breakout: the attacker lands on the node, next to everything else on it.

[Kata Containers](https://katacontainers.io/) change that boundary. Each pod runs inside a lightweight virtual machine with its own guest kernel. From Kubernetes' point of view it's still a pod; underneath, there's a hypervisor between the agent and the host. To get out, an attacker now needs a hypervisor escape, which is a much rarer and much more expensive bug than a kernel one.

In Kubernetes you opt a pod into Kata with a `RuntimeClass`. The shape of it:

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata
handler: kata   # matches the runtime name Kata registered with containerd
---
apiVersion: v1
kind: Pod
metadata:
  name: agent
spec:
  runtimeClassName: kata   # this pod gets its own microVM and guest kernel
  containers:
    - name: claude-code
      image: ghcr.io/example/agent:latest
```

The cost is a little memory per pod and a slightly slower start. For a handful of agent sandboxes, that's an easy trade.

## Control: approvals on my phone, no open ports

I don't SSH into these pods, and they don't listen on anything. I drive the agents from my phone using Claude Code's Remote Control.

The agent inside the pod makes **outbound** HTTPS connections to Anthropic's API, and my phone talks to the same relay. Nothing on the homelab is exposed to the internet, there are no inbound ports, and there's no tunnel for someone else to find.

The part that matters most is permissions. When the agent wants to do something that needs approval, like running a command or editing a file outside what I've allowed, the request shows up on my phone. I read it and approve or reject it *before* it runs. The sandbox limits the blast radius; the approval step keeps a human in the loop for anything sensitive.

## What the agents actually do

### Cluster debugging

This is most of what I use them for: a `CrashLoopBackOff`, a rollout stuck at 10%, a pod that won't schedule. The agent reads pod logs and events, describes resources, compares what's running with what's in Git, and traces the failure back to a root cause.

It does all of that through a **read-only** ServiceAccount. It can inspect almost everything and change nothing. This is the actual config from my GitOps repo, synced by Argo CD:

```yaml
# Identity for AI/automation agents that need to inspect the cluster but
# never change it. Issue short-lived tokens rather than a long-lived Secret:
#   kubectl -n default create token agent-read-only --duration=24h
apiVersion: v1
kind: ServiceAccount
metadata:
  name: agent-read-only
  namespace: default
---
# Built-in `view`: read most namespaced objects in every namespace.
# Excludes Secrets, pods/exec and port-forward.
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: agent-read-only-view
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: view
subjects:
  - kind: ServiceAccount
    name: agent-read-only
    namespace: default
```

The built-in `view` role is a good start, but it only covers namespaced objects. Debugging often needs nodes, storage classes, webhooks, RBAC itself and CRDs, so a second ClusterRole fills those gaps, with read verbs only:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: agent-cluster-read
rules:
  - apiGroups: [""]
    resources: ["nodes", "persistentvolumes", "namespaces"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["admissionregistration.k8s.io"]
    resources: ["validatingwebhookconfigurations", "mutatingwebhookconfigurations"]
    verbs: ["get", "list", "watch"]
  # Who-can-do-what, for debugging permission errors.
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
    verbs: ["get", "list", "watch"]
  # CRDs in this cluster: Argo, Gateway API, Traefik, Prometheus, cert-manager...
  - apiGroups: ["argoproj.io", "gateway.networking.k8s.io", "monitoring.coreos.com"]
    resources: ["*"]
    verbs: ["get", "list", "watch"]
```

Two rules I hold to here. Every rule names its API group: `resources: ["*"]` on the core group would quietly include Secrets. And tokens are short-lived, minted with `kubectl create token --duration=24h`, so a leaked token expires on its own.

### Opening PRs

A diagnosis is only half the job. The other half is the fix, and for my cluster the fix almost always lives in Git: a manifest change, a Helm value, a config tweak.

So the agent turns its diagnosis into a pull request on my GitOps repo. It pushes with a **fine-grained, repo-scoped token** that can open branches and PRs on that one repository and nothing else. Branch protection on `main` means a human always merges. Argo CD only syncs what's on `main`, so nothing an agent writes reaches the cluster until I've read it.

That split is deliberate. The agent's cluster credentials can read but not write, and its Git credentials can propose but not merge. To change anything, you need both an agent's work and my review.

### Parallel work

Each agent session gets its own **git worktree**: a separate checkout of the same repository on its own branch. Two sessions can work on two different problems at once without fighting over files, and each one ends up as its own branch and its own PR.

## Guardrails

Isolation alone isn't enough. An agent in a perfect sandbox, holding an admin token, can still do a lot of damage through the API. These are the other layers:

- **Least privilege everywhere.** Read-only RBAC for the cluster, fine-grained tokens for GitHub, nothing shared between sessions.
- **Egress allowlisting.** The sandbox can only reach the hosts it needs: the model API, GitHub, the Kubernetes API, a package registry. Everything else is blocked, which closes the easiest exfiltration path, an agent tricked into `curl`ing your secrets to someone else's server. Kubernetes NetworkPolicies work on IPs and ports, so the baseline is a default-deny egress policy, with allowing specific hostnames left to an egress proxy or an FQDN-aware CNI.
- **Ephemeral sandboxes.** Pods are disposable. Anything worth keeping lives in a PVC or in Git, so if a sandbox looks wrong, I delete it and start a clean one. Anything planted outside that PVC is gone with the pod, and changes to Git go through review.

A default-deny egress policy is a few lines:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: agent-egress
spec:
  podSelector:
    matchLabels:
      app: agent
  policyTypes: ["Egress"]
  egress:
    # DNS
    - ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
    # HTTPS only; narrow `to:` further, or route it through an egress proxy
    - ports:
        - { protocol: TCP, port: 443 }
```

## The takeaway

None of this is specific to AI. It's the same thinking you'd apply to any workload that runs code you didn't write:

- **Isolation limits where damage can happen.** A microVM keeps a compromised agent inside its own kernel.
- **Scoped credentials limit how much.** Read-only cluster access and propose-only Git access mean even a fully compromised agent can look around and open a PR, and that's it.
- **A human approves the sensitive parts.** Permission prompts on my phone, and merges on GitHub.

Running agents safely isn't a prompt engineering problem. It's a platform engineering problem.
