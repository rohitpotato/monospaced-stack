> **TL;DR:** I run AI coding agents inside my homelab Kubernetes cluster and drive them from my phone with Claude Code's Remote Control. They debug failing pods, turn the fix into a pull request, and work on several things at once. Each one lives in its own microVM with read-only cluster access, so I can say "yes, go ahead" from the couch without worrying about it.

Most of my cluster problems don't happen while I'm at my desk. A deployment starts crash-looping, an alert fires, and the usual routine is: find a laptop, open a terminal, start digging through logs.

These days I open the Claude app on my phone instead. An agent that already lives inside the cluster does the digging, explains what it found, and suggests a fix. When it wants to run something that needs my OK, I get a prompt on my phone. When the fix is ready, it opens a pull request, and I merge it whenever I'm back.

This post is how that setup works: where the agents run, what they're allowed to do, and why I'm comfortable letting them run real commands on my cluster.

## Driving agents from my phone

The agents are Claude Code sessions running in pods on my cluster. I connect to them with Claude Code's **Remote Control**, which lets me pick up a session from the Claude app on my phone, or from a browser, as if I were sitting at the terminal.

Here's what that looks like in practice. Say a pod is stuck in `CrashLoopBackOff` while I'm out:

1. I open the session on my phone and type something like *"the frontend pods are crash-looping, find out why"*.
2. The agent reads the pod's events and logs, checks the deployment and its recent changes in Git, and narrows it down: a bad config value, a missing secret reference, an image that won't start.
3. Anything that needs permission, like running a command I haven't pre-approved, shows up on my phone as a prompt. I read it and tap approve or reject.
4. Once it knows the cause, it writes the fix and opens a pull request. I review the diff on my phone, or later on a bigger screen, and merge it.

The best part of this is what *isn't* there. The pod never accepts incoming connections. It only makes **outbound** HTTPS connections to Anthropic's API, and my phone talks to the same relay. There are no open ports on my homelab, no VPN to set up, and no SSH to expose. If my phone can reach the internet, I can reach my agents.

## What the agents do

### Debug the cluster

This is most of what I use them for: crash loops, rollouts stuck at 10%, pods that won't schedule, a service returning errors after a deploy. The agent reads logs and events, describes resources, compares what's running with what's in Git, and traces the failure back to a cause.

It does all of this through a **read-only** ServiceAccount. It can look at almost everything and change nothing. This is the actual config from my GitOps repo:

```yaml
# Identity for AI/automation agents that need to inspect the cluster but
# never change it. Issue short-lived tokens rather than a long-lived Secret:
#   kubectl -n default create token agent-read-only --duration=24h
apiVersion: v1
kind: ServiceAccount
metadata:
  name: agent-read-only
  namespace: default
---
# Built-in `view`: read most namespaced objects in every namespace.
# Excludes Secrets, pods/exec and port-forward.
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: agent-read-only-view
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: view
subjects:
  - kind: ServiceAccount
    name: agent-read-only
    namespace: default
```

The built-in `view` role covers namespaced objects. A second, small ClusterRole adds read access to the cluster-wide things debugging needs: nodes, storage classes, webhooks, RBAC and the CRDs I use (Argo CD, Gateway API, Prometheus). Read verbs only, and never Secrets.

### Open pull requests

A diagnosis is only half the job. For my cluster, the fix almost always lives in Git: a manifest change, a Helm value, a config tweak. So the agent turns what it found into a pull request on my GitOps repo.

It pushes with a token that can only open branches and pull requests on that one repository. `main` is protected, so I'm always the one who merges, and Argo CD only deploys what's on `main`. Nothing an agent writes reaches the cluster until I've read it.

### Work on several things at once

Each session gets its own **git worktree**, a separate checkout of the same repository on its own branch. I can have one agent chasing a crash loop and another updating a Helm chart, and they never step on each other's files. Each ends up as its own branch and its own pull request.

## Keeping them contained

Letting an agent run commands on your cluster from your phone only feels relaxed if you know what it *can't* do. Agents read a lot of text, like READMEs, issue comments and logs, and some of that text could try to talk them into something. So I set things up so that even a confused agent can't do much damage:

- **Its own microVM.** Each agent runs in a [Kata Container](https://katacontainers.io/): a pod that runs inside a lightweight virtual machine with its own kernel. A normal container shares the host's kernel, so a kernel bug could let it out onto the node. With Kata, there's a hypervisor in the way. In Kubernetes it's one line in the pod spec, `runtimeClassName: kata`.
- **Credentials that can look, or propose, but not act.** The cluster token is read-only. The Git token can open pull requests but not merge them. To change anything, you need both the agent's work and my review.
- **Limited network access.** The pod can reach only what it needs: the model API, GitHub, the Kubernetes API and package registries.
- **Throwaway sandboxes.** Pods are disposable. Anything worth keeping lives in a volume or in Git, so if a sandbox ever looks off, I delete it and start a fresh one.

## The takeaway

The reason I can run agents from my phone is that the platform does the worrying for me. The microVM decides *where* an agent can cause trouble, and its credentials decide *how much*. With those in place, approving a step on my phone is a quick decision, not a risky one.

That's what made this useful rather than nerve-wracking: give agents a safe place to work, and you can hand them real tasks.
